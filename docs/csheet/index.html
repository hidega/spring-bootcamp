Memory

class method area stores per-class structures such as the runtime constant pool, field and method data, and the code for methods.
heap is created a runtime and it contains the runtime data area in which objects are allocated. The string pool is a part of the heap.
stack stores local variables and partial results at runtime. Each thread creates a private JVM stack at the time of thread creation.
native method stack is reserved for all the native methods used in the application.
Pass by value
Arguments in Java are always passed-by-value. During method invocation, a copy of each argument, whether its a value or reference, is created in stack memory which is then passed to the method.
In case of primitives, the value is simply copied inside stack memory which is then passed to the callee method. In case of non-primitives, a reference in stack memory points to the actual data which resides in the heap. When we pass an object, the reference in stack memory is copied and the new reference is passed to the method.
Processes and threads
In Java, a process refers to the running of Java Virtual Machine (JVM). A thread in Java is a lightweight process that runs within another process. A thread lives within a JVM and it can be created or stopped by the Java application at runtime.
Monitor
A monitor is a synchronization mechanism that allows threads to have: - mutual exclusion: only one thread can execute the method at a certain point in time, using locks, - cooperation: the ability to make threads wait for certain conditions to be met, using wait-set. Monitors provide three main features to the concurrent programming: - only one thread at a time has mutually exclusive access to a critical code section, - threads running in a monitor could be blocked while they’re waiting for certain conditions to be met, - one thread can notify other threads when conditions they’re waiting on are met. A critical section is a part of the code that accesses the same data through different threads. In Java, we use the synchronized keyword to mark critical sections.
Garbage collection
Java has an automated process called Garbage Collector for memory management. It is a daemon in JVM that monitors memory usage and performs memory cleanup. Once the JVM is low on memory, the GC process finds the unused objects that are not referenced by other objects, then these unused objects are cleaned up by Garbage Collector daemon in JVM.
An object can be garbage collected if it is not reachable. There are two cases for deciding eligibility of objects for Garbage Collection. (i) when an object instance that cannot be reached by a live thread, (ii) or a set of circularly referenced instances that cannot be reached by any other instance outside that set.

Default methods
Default methods in an interface provide backward compatibility feature in Java 8.
Let say there is an interface Car that is implemented by BMW, Chevrolet and Toyota classes. Now a Car needs to add capability for flying. It will require change in Car interface. Some of the car classes that do not have flying capability may fail. Therefore a default implementation of flying methods is added in Car interface so that cars with no flying capability can continue to implement the original Car interface.
Java prevents the traditional "Diamond Problem" of multiple class inheritance, but default methods allow a form of multiple inheritance that can cause ambiguity. When an implementing class inherits conflicting default methods, the Java compiler forces you to explicitly resolve the collision.

Polymorphism in Java
In Java, method overloading means that a class can have multiple methods with same name but different arguments. To override a method, we just provide a new implementation of a method with same name in a subclass. Java does not allow overriding a static method. If you create a static method with same name in subclass, then it is a new method, not an overridden method (to override a method, you need an instance of a class).
runtime polymorphism (or dynamic polymorphism) is the case when method overriding occurs but it is not known which method will be called at runtime. Based on the type of object, JVM decides the exact method that should be called. We create runtime polymorphism by implementing methods at two levels of inheritance in Java.

Aggregtion composition
Aggregation and composition are association relations types. Composition is a strong relationship. If the composite object is destroyed, then all its parts are destroyed. Aggregation is a weaker relationship than composition.
E.g. a library has students. If a library is destroyed, students still exist. So library and student are related by aggregation. A library has books. If a library is destroyed, the books are also destroyed. Books of a library cannot exist without the library. So book and library are related by composition.

Deadlock
The minimum requirements for a Deadlock situation in a program are
- Mutual exclusion There has to be a resource that can be accessed by only one thread at any point of time.
- Resource holding One thread locks one resource and holds it, and at the same time it tries to acquire lock on another mutually exclusive resource.
- No preemption There is no pre-emption mechanism by which resource held by a thread can be freed after a specific period of time.
- Circular wait There can be a scenario in which two or more threads lock one resource each and they wait for each other’s resource to get free. This causes circular wait among threads for same set of resources.
Deadlock prevention
At least one requirement for a deadlock has to be removed.
- Mutual exclusion: We can use optimistic locking to prevent mutual exclusion among resources.
- Resource holding: A thread has to release all its exclusive locks if it does not succeed in acquiring all exclusive locks for resources required.
- No preemption: We can use timeout period for an exclusive lock to get free after a given amount of time.
- Circular wait: We can check and ensure that circular wait does not occur, when all exclusive locks have been acquired by all the threads in the same sequence.
Livelock
Livelock is a scenario in which two or more threads block each other by responding to an action caused by another thread. In a deadlock situation two or more threads wait in one specific state. In a Livelock scenario, two more threads change their state in such a way that it prevents progress on their regular work. Consider a scenario in which two threads try to acquire two locks. They release a lock that they have acquired, when they cannot acquire the second lock. In a Livelock situation, both threads concurrently try to acquire the locks. Only one thread would succeed, the second thread may succeed in acquiring the second lock. Now both threads hold two different locks, and both threads want to have both locks. So they release their lock and try again from the beginning. This situation keeps repeating multiple times.
Thread starvation
In a priority based scheduling, threads with lower priority get lesser time for execution than higher priority threads. If a lower priority thread performs a long running computation, it may happen that this thread does not get enough time to finish its computations just in time. In such a scenario, the thread with lower priority would starve. It will fall back from the threads with higher priority.
Race condition
A race condition arises when multiple processes or threads are simultaneously trying to modify and retrieve shared data, resulting in unforeseen and unintentional outcomes.
The consumer/producer problem
The problem describes two processes, the producer and the consumer, who share a common, fixed-size buffer used as a queue. The producer's job is to generate data, put it into the buffer and start again. At the same time, the consumer is consuming the data (i.e. removing it from the buffer), one piece at a time. The problem is to make sure that the producer won't try to add data into the buffer, if it's full and that the consumer won't try to remove data from an empty buffer.
The solution for the producer is to either go to sleep or discard data if the buffer is full. The next time the consumer removes an item from the buffer, it notifies the producer, who starts to fill the buffer again. In the same way, the consumer can go to sleep if it finds the buffer empty. The next time the producer puts data into the buffer, it wakes up the sleeping consumer.

A thread-safe singleton class
public class A {
  private A() {}
  private static volatile A instance;
  public A getInstance() {
    A localRef = instance;
    if (localRef == null) {
      synchronized (A.class) {
        localRef = instance;
        if(localRef == null) {
          instance = localRef = new A();
        }
      }
    }
    return localRef;
  }
}
A non thread-safe singleton class
public class SingletonDoubleCheck {
  private SingletonDoubleCheck instance = null;
  public SingletonDoubleCheck getInstance() {
    if (instance == null) {
      synchronized (SingletonDoubleCheck.class) {
        if (instance == null) {
          instance = new SingletonDoubleCheck();
        }
      }
    }
    return instance;
  }
}
We check the value of instance second time in the synchronized block. But the JIT compiler can rearrange the bytecode in such a way that the reference to SingletonDoubleCheck instance will be set before the execution of constructor. Due to this the method getInstance() will return an object that may not have been initialized properly. We can use the keyword volatile for instance to make this threadsafe code. Any variables that is marked as volatile will be visible to other threads only after the completion of the constructor of the object.
Thread
A thread in Java is a lightweight process that runs within another process. There are two types of threads. native threads (aka. platform threads) are managed and scheduled by the operating system, whereas virtual threads are managed and scheduled by the JVM. Virtual threads are available since Java 25. Each thread has its own method-call stack. When we start JVM, Java starts one thread. This thread calls the main method of the class passed as an argument of the java command.
Thread priority
In Java, every thread has a priority. This priority is specified as a number between 1 to 10. We can set following three priorities on a Thread object in Java. Default priority of a thread is NORM_PRIORITY = 5. The value of MIN_PRIORITY is 1 and the value of MAX_PRIORITY is 10. Scheduler in Java schedules different threads based on the priority of a thread. It is also known as pre-emptive scheduling. The thread with higher priority gets preference in execution over a thread with lower priority.
States of a thread
A Java thread can exist in one of six distinct states, defined by the Thread.State enum.
NEW: A thread that has been created but not yet started via thread.start().
RUNNABLE: A thread executing in the Java virtual machine. It is either actively running or sitting in the operating system's dispatch queue waiting for CPU resources.
BLOCKED: A thread waiting for a monitor lock to enter or re-enter a synchronized block or method.
WAITING: A thread waiting indefinitely for another thread to perform a specific action (e.g., notifying or joining).
TIMED_WAITING: A thread waiting for another thread to perform an action for up to a specified waiting time.
State transitions of a thread
1. Object::wait() and Object::notify() or notifyAll()
The wait mechanism requires the calling thread to hold the object's monitor lock. Invoking object.wait() drops the monitor lock and moves the thread from RUNNABLE to WAITING. If a timeout is provided with object.wait(long), it moves to TIMED_WAITING. When another thread holds the same lock and calls object.notify() or object.notifyAll(), the waiting thread is awakened. It moves to BLOCKED because it must re-acquire the monitor lock before it can resume execution. Once the lock is acquired, it returns to RUNNABLE.
2. Thread::interrupt()
(i) If the thread is in WAITING or TIMED_WAITING: Calling thread.interrupt() wakes the thread up. It clears the interrupt status, transitions the thread to BLOCKED to re-acquire any necessary locks, and then to RUNNABLE where a InterruptedException is immediately thrown. (ii) If the thread is BLOCKED on a monitor lock: Calling interrupt() sets the thread's interrupt flag, but it does not break the thread out of the blocked state. The thread remains BLOCKED until it acquires the lock. (iii) If the thread is RUNNABLE: Calling interrupt() does not interrupt physical execution.
3. Thread::sleep(long)
Invoking Thread.sleep(millis) immediately moves the current thread from RUNNABLE to TIMED_WAITING. Unlike Object.wait(), Thread.sleep() does not release any monitor locks the thread currently holds. When the timer expires, it returns directly to RUNNABLE.
4. Thread::join() and Thread::join(long)
Called on a target thread instance eg. threadB.join(), this moves the calling thread from RUNNABLE to WAITING or TIMED_WAITING if a timeout is passed. When threadB finishes and enters the TERMINATED state, the JVM automatically signals any threads waiting on its monitor, moving the calling thread back to RUNNABLE.
5. LockSupport::park() and LockSupport::unpark(Thread)

Notable Executors
- SingleThreadExecutor has only one thread and is used to execute tasks in a sequential manner. If the thread dies due to an exception while executing the task, a new thread is created to replace the old thread and the subsequent tasks are executed in the new thread.
- FixedThreadPoolExecutor is an executor with a fixed number of threads. The tasks submitted to this executor are executed by the specified number of threads and if there are more tasks than the number of threads, then those tasks will be added in a queue.
- CachedThreadPoolExecutor is mainly used when there are many short-lived tasks to be executed. The number of threads of this executor pool is not bounded.
- ScheduledExecutor can be used when you want to schedule your tasks, like run them at regular intervals or run them after a given delay.
- ScheduledThreadPoolExecutor It extends ThreadPoolExecutor and uses a specialized delayed work queue. In comparison with java.util.Timer, Timer is single-threaded and kills the whole timer if a task throws an uncaught exception. ScheduledThreadPoolExecutor handles multi-threading and misbehaving tasks safely.
- Executors.newVirtualThreadPerTaskExecutor() The modern executor for handling concurrent I/O-heavy workloads. It does not pool threads because virtual threads are so cheap. Instead, it spins up an entirely new, lightweight virtual thread for every single submitted task and tears it down immediately when finished. It implements AutoCloseable.
- Executors.newWorkStealingPool(int parallelism) Each worker thread has its own double-ended queue of tasks. If a thread runs out of its own work, it "steals" tasks from the back of other threads' deques. It minimizes thread contention and context-switching overhead.
- ForkJoinPool.commonPool() A globally shared, static work-stealing pool managed by the JVM. To be used with CompletableFuture without explicitly providing an executor.
Executor and ExecutorService
The Executor interface has a single execute(Runnable) method. The implementing class of this interface has to execute the given Runnable instance passed to execute() method at some time in the future. The ExecutorService interface extends Executor interface. It provides additional methods like invokeAny(), invokeAll(), shutdown(), awaitTermination(), submit(Future). These methods can be use to shutdown the thread so that further requests can be rejected. The fork/join framework
The ForkJoinPool class is in the center of fork/join framework. It is a thread pool that can execute instances of ForkJoinTask. The ForkJoinTask class provides the fork() and join() methods. fork() is used to start the asynchronous execution of a task. join() is used to await the result of the computation.
ThreadLocal and ScopedValue classes
A thread local variable is a variable restricted to a specific thread. It is like the thread's own copy of a variable that is not shared among multiple threads.
The ThreadLocal class provides support for thread-local variables. Each thread accesses only its own local variables. If thread X stores a variable with value x and another thread Y stores same variable with the value y, then X gets x from its ThreadLocal instance and Y gets y from its ThreadLocal instance. Typically, ThreadLocal instances are private static fields that are associated with the state of a thread.
Since Java 25, the ScopedValue class is recommended to manage thread-local variables.
The yield method
The Thread.yield method is used to temporarily pause the currently executing thread and give a chance for other threads of the same or higher priority to execute. When a thread calls Thread.yield, it goes back to the Runnable state.

REST
The principles of REST (REpresentational State Transfer) are Uniform interface principle, Client–server principle, Stateless principle, Cacheable principle, Layered system principle.
REST Cacheable principle
In REST, caching shall be applied to resources when applicable, and then these resources must declare themselves cacheable. Caching can be implemented on the server or client-side.
REST Layered system principle
It means that you deploy the APIs on server A, and store data on server B and authenticate requests in Server C, for example. A client cannot ordinarily tell whether it is connected directly to the end server or an intermediary along the way.
REST Uniform interface principle
One must decide APIs interface for resources inside the system which are exposed to API consumers. A resource in the system should have only one logical URI, and that should provide a way to fetch related or additional data. Any single resource should not be too large and contain each and everything in its representation. Whenever relevant, a resource should contain links pointing to relative URIs to fetch related information.Also, the resource representations across the system should follow specific guidelines such as naming conventions, link formats, or data format (XML or/and JSON). All resources should be accessible through a common approach such as HTTP GET and similarly modified using a consistent approach.
REST Client server principle
This constraint essentially means that client applications and server applications must be able to evolve separately without any dependency on each other. A client should know only resource URIs, and that’s all. Servers and clients may also be replaced and developed independently, as long as the interface between them is not altered.
REST Stateless principle
Make all client-server interactions stateless. The server will not store anything about the latest HTTP request the client made. It will treat every request as new. No session, no history. No client context shall be stored on the server between requests. The client is responsible for managing the state of the application.
SOLID
The SOLID ideas are
- The Single-responsibility principle: "There should never be more than one reason for a class to change." In other words, every class should have only one responsibility.
- The Open–closed principle: "Software entities ... should be open for extension, but closed for modification."
- The Liskov substitution principle: "Functions that use pointers or references to base classes must be able to use objects of derived classes without knowing it."
- The Interface segregation principle: "Clients should not be forced to depend upon interfaces that they do not use."
- The Dependency inversion principle: "Depend upon abstractions, [not] concretions." Ensures loosely coupled components

Microservice Database Patterns
Database per service pattern
CQRS pattern: The command query responsibility segregation (CQRS) pattern can be useful if you have a large application reading data from an event store. It separates read and update operations, which can otherwise be difficult when processing all entities but only fetching a single one.
Saga pattern: Saga is a microservices design option that allows developers to manage eCommerce transactions across multiple microservices using a sequence of local transactions. Each of these is accompanied by an event that will trigger the next stage. If one transaction fails, this approach can trigger a rollback transaction to compensate for the failure. One of the biggest problems is how to work around transactions that span multiple services. The saga pattern can help with this.
Event sourcing pattern: Using a messaging system.
Microservice Observability Patterns
Log aggregation pattern, Performance metrics pattern, Distributed tracing pattern, Health check pattern
Microservice Cross cutting concerns Patterns
Extrenal configuration pattern
Service discovery pattern
Circuit breaker pattern: The circuit breaker trips when the number of failures reaches a certain level, and any subsequent calls to the breaker result in an error, a different service, or a default message instead of the protected call being made.
Blue green deployment pattern: Running two identical production environments: blue and green. Green is the existing live instance, and blue is the new version of the application. Only one of the environments is live at any time, with the live environment serving all production traffic.
Database theory
ACID
Atomicity guarantees that each transaction is treated as a single "unit", which either succeeds completely or fails completely.
Consistency ensures that a transaction can only bring the database from one consistent state to another, preserving database invariants: any data written to the database must be valid according to all defined rules, including constraints, cascades, triggers, and any combination thereof.
Isolation ensures that concurrent execution of transactions leaves the database in the same state that would have been obtained if the transactions were executed sequentially.
Durability guarantees that once a transaction has been committed, it will remain committed even in the case of a system failure.
CAP
The CAP theorem states that any distributed data store can provide only two of the following three guarantees:
Consistency: Every read receives the most recent write or an error.
Availability: Every request receives a (non-error) response, without the guarantee that it contains the most recent write.
Partition tolerance: The system continues to operate despite an arbitrary number of messages being dropped (or delayed) by the network between nodes.
Isolation levels
With a lock-based concurrency control DBMS implementation: Serializable level requires read and write locks (acquired on selected data) to be released at the end of the transaction. Also range-locks must be acquired when a SELECT query uses a ranged WHERE clause, especially to avoid phantom reads. A serializable execution is defined to be an execution of the operations of concurrently executing SQL-transactions that produces the same effect as some serial execution of those same SQL-transactions.
Repeatable reads: The DBMS keeps read and write locks (acquired on selected data) until the end of the transaction. However, range-locks are not managed, so phantom reads can occur. Write skew is possible at this isolation level, which means that two writes are allowed to the same column(s) in a table by two different writers (who have previously read the columns they are updating), resulting in the column having data that is a mix of the two transactions.
Read committed level guarantees that any data read is committed at the moment it is read. It restricts the reader from seeing any intermediate, uncommitted, 'dirty' read. It makes no promise whatsoever that if the transaction re-issues the read, it will find the same data; ie. data is free to change after it is read.
Read uncommitted level allows dirty reads which means that one transaction may see not-yet-committed changes made by other transactions.
